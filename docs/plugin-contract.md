# 插件约定

本文件定义设计边界，当前不提供已实现的 SDK、运行器或稳定协议。新增接口时需要补源码、版本和验证，不应直接把本文示例当作现存命令。

## 接入层次

| 层次 | 内容 | 适用范围 |
| --- | --- | --- |
| 快捷命令 | 参数、目标、执行方式、退出结果 | 简单查询、用户自有脚本 |
| 功能插件 | 系统探测、操作列表、结构化表单与结果 | 服务管理、配置与诊断 |
| 工作流插件 | 多阶段执行、检查、等待输入、恢复契约 | 初始化、加固、安装、备份恢复 |

快捷命令不必包装成完整插件。需要人工交互的脚本在新终端显式执行；后台任务不能偷偷控制现有终端。

## 最小契约方向

实现时优先定义以下内容，不预先扩展成通用插件平台：

- 插件 ID、名称、版本、SDK 兼容范围。
- 支持的远程系统、架构、服务管理器，以及权限需求。
- 只读能力探测：区分已安装、未安装、不支持、未知和探测失败。
- 操作 ID、参数校验、目标类型、是否修改远端、冲突资源。
- 有限核心服务上下文：受控执行、文件传输、事件、日志和访问保护。
- 事件与结果：步骤、进度、警告、需用户输入、退出状态、结构化输出。
- 超时、取消、可重试条件、幂等性，以及明确可用的恢复或补偿动作。

机器接口需要版本号或兼容能力协商。探测失败不等同于未安装，不能因探测失败自动重装。

## 核心与插件分工

| 核心 | 插件 |
| --- | --- |
| 主机与认证引用、主机指纹 | 具体服务的能力探测与配置参数 |
| SSH 会话、执行和传输能力 | 操作步骤与结果解释 |
| 任务调度、资源锁、事件与记录 | 声明操作影响、冲突资源与恢复条件 |
| 统一访问保护与连接验证 | 调用保护流程完成具体 SSH/防火墙变更 |
| 统一 UI、表单和任务展示 | 提供表单定义，必要时提供专用页面 |

插件不得另起凭据仓库、直接读写核心数据库、读取其他终端输入或绕过任务引擎执行批量操作。任意第三方代码不因声明权限就获得真正隔离；初期只运行项目维护的可信内置插件。

需要专用界面时分开导出 Renderer 与后台入口，防止后台依赖进入前端包。

## 首批插件

### Diagnostics

提供系统信息和诊断。默认采用只读检查，输出结构化状态与检查时间。查询结果可能包含主机信息，持久日志和导出前需要脱敏。

### Access

提供公钥接入、登录配置和访问路径调整，使用核心访问保护、独立新连接验证和资源锁。具体系统修改属于插件，指纹信任和凭据属于核心。

### SuRelay

只负责适配独立 SuRelay 工具，不复制服务端代码，不依赖开发机的兄弟项目路径，不因插件加载而自动安装或升级服务。

已知现有 SuRelay 提供 `install.sh`、分阶段 `bootstrap.sh`、`sr` 菜单及少量直接命令；不能假设已有完整 JSON 接口。

接入顺序建议：

1. 探测安装、版本和能力，只读呈现状态。
2. 对成熟且非交互的操作建立明确退出结果和结构化输出适配。
3. 与 SuRelay 独立项目协作补机器接口，保留其人工终端使用方式。
4. 接入安装、访问保护和恢复等多阶段操作，并验证失败边界。

SuRelay 现有 SSH/防火墙功能与 Access 插件存在范围交叉，应统一走核心的资源锁和访问保护。机器接口未就绪时可以提供显式的“在新终端中打开 SuRelay”，不能解析菜单坐标或自动按键冒充稳定协议。
